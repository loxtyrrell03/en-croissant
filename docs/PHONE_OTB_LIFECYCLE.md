# Phone OTB result lifetime

The PC job ID remains selected after Stop. If completion won the race, its saved artifact still loads and the games remain usable. If the PC confirmed a stopped/failed job, that result is visible and another search can be started. Cancellation does not request deletion of an artifact. The PC service intentionally terminates an active collector and reports a failed/stopped job; it does not promise desktop-style partial source results. This server contract is unchanged.

A Stop response invalidates an older shared status GET before starting a fresh observation. An abandoned request cannot replace the new result, clear its in-flight ownership or publish a late error. Status replies validate identity, supported state and supplied request metadata; completed jobs require usable player/year metadata. Compact completed status is distinct from an artifact already loaded: pending or failed artifact reads do not claim there are zero usable games. Shared watchers continue retrying read failures. Errors from Stop or Analyze survive ordinary status refreshes.

The phone waits for a stored job to load before allowing another search and restores that job's player, FIDE ID and year. Stop and Analyze have synchronous request guards and reject late component updates after unmount. A pending Stop never clears another view's persisted job selection. Completed games and source totals retain their scope. The panel reports PC-ready games; it no longer guesses browser/Prep handoff success from a storage receipt or says Saving indefinitely. Automatic Prep persistence is covered below; malformed artifacts and missing-job recovery remain follow-ups.

The existing Mantine interface now wraps source/search button labels and shows complete game names and event metadata on narrow screens. The PC explanation is shorter and retains the need to leave the PC on. Source selectors, year controls, Stop, Analyze and saved result access remain available. This is a small correction within the existing phone design, not a new visual system.

## Recoverable PC start endpoint

`PUT /api/otb-import/jobs/otb-<UUID-v4>` accepts the same normalized search payload as the existing POST endpoint. The client must generate and durably retain the job ID and original request before sending it. A retry must use that exact ID and payload. There is no automatic fallback to POST: older PC services return 405 for this new route, which is a visible compatibility error in the phone integration. The phone integration below now persists and sends those recoverable requests.

The service owns each ID before asynchronous availability/storage checks, so concurrent retries join one start. Changing the player, FIDE ID, start year or selected sources for an existing/pending ID returns 409. Invalid client IDs return 400; the generated legacy POST IDs remain supported for reads and cancellation. Existing running, completed and stopped jobs are returned without another collector, even if the native binary is no longer installed. Repeated requests preserve result artifacts and completion timestamps. Explicit new searches use new IDs.

An initial save failure launches nothing and can retry the same queued destination. A synchronous pre-process launch failure can also retry. If the process was launched but its status save failed, a retry persists that existing job instead of spawning again. Stop that completes during an initial save prevents a later launch. These guarantees cover retries within the owning service and saved jobs loaded by its existing restart recovery. They do not claim an atomic process-spawn/filesystem transaction: a crash before the PID becomes durable retains the existing recovery limitation. Restarted interrupted jobs remain failed and require an intentional new search; retrying their old IDs never restarts them.

## Phone request ownership and retry

The phone now uses the recoverable PUT endpoint. `otbStartSession.ts` owns the complete versioned `encroissant-web-otb-start` record: random UUID, original player/FIDE/year/sources, PC endpoint and acknowledgement state. A durable write must succeed before any start is sent. One session promise remains alive when the import view closes; returning to the view observes that same operation. After a full reload, an unacknowledged record restores its fields and offers Retry connection. Retry never reruns FIDE resolution or substitutes edited input, a new ID or POST. Older PC services return an actionable update error. A different request/ID in the start reply is rejected.

A failed confirmation write keeps the already-saved request. The known PC job remains usable within the session, and retry saves its acknowledgement without another network start; after reload, PUT recovers that same ID. The acknowledged record is authoritative. Failure to update the legacy ID mirror cannot undo it, and WebApp now subscribes to the shared selection rather than polling that mirror. Receipt reads in its existing Prep callback are caught so they cannot escape through this subscription; the complete automatic Prep/state-persistence workflow is not certified by this change and remains below.

Same-origin storage changes update other open views. [Web Locks](https://www.w3.org/TR/web-locks/) coordinate the short synchronous selection writes; no network request holds a lock. A changed ID/request prevents a late reply from replacing newer selection. A pending record prevents another tab from silently replacing the uncertain search. New starts/reconnections require secure browser support for Web Locks and UUID generation; unsupported contexts expose guidance before mutation. Previously saved job reads remain available. Corrupt records and records belonging to another PC endpoint are preserved and refused, not overwritten. The subsequent tracking-recovery section records their explicit review/copy path.

Start/status/Stop responses and JSON bodies have a 15-second deadline with cancellation propagation. Artifact bodies have a separate ten-minute bound so the small-status deadline does not interrupt large saved results. A timeout keeps the PC identity and permits another read; it does not stop or delete the independent PC collector. Downloads are retried from the beginning; range resumption and stalled-transfer progress remain broader performance/UX follow-ups.

The phone shows one Connecting/Retry action while a start is uncertain and explains that retry reconnects to the same search. Fields and source controls remain locked to that request. Locked input text now uses the existing theme's readable text colour, and the narrow input font follows the user's Mantine scale rather than staying fixed at 16px. The form's existing layout, sources, Stop and game actions are retained.

## Workspace commits and automatic OTB handoff

The phone's browser workspace now treats IndexedDB transaction completion as the save acknowledgement. A successful put request can still be followed by an abort; see the [IndexedDB transaction contract](https://www.w3.org/TR/IndexedDB/#dom-idbtransaction-oncomplete). Failed, blocked or expired database opens can retry; late connections close, version changes release the connection, and stalled transactions abort after a separate 60-second bound. Missing state creates a new workspace, while invalid stored state remains untouched and cannot open an editable empty replacement. Existing optional board/Prep defaults remain normalized.

`webStateSession.ts` owns one immutable snapshot and serialized writer for the browser tab. The first edit and edits made during a pending write are saved; a failed save retains the newest draft across view/root remount and exposes a persistent Retry save action. Loading failure gates the workspace and file import until Retry loading succeeds. Pending writes receive best-effort pagehide/visibility flushing and a beforeunload prompt where supported. A service-worker/version check cannot reload an unready or unsaved workspace, or a disposed root; a later check may adopt the build after successful recovery. Browser termination before commit is not a persistence guarantee.

Automatic OTB import adds `completedOtbImports` to the existing version-one state. Games, Prep and receipt share the same transaction. Only a completed save produces the saved notification; failures use the workspace's retained Retry save rather than reapplying the PC artifact. A replay does not replace edited games or resurrect deliberately removed collections/Prep. Existing `prep-<jobId>` workspaces migrate their receipt without merging the original artifact over later annotations. The old separate localStorage receipt is no longer used by WebApp. Background completion keeps the current view and board; imported games remain under Import. This optional browser field does not alter native database formats or PC importer protocols. Novelty's separate native saved-game checkpoint/dedupe contract remains documented in its own audit; En desktop conversion needs independent work.

## Reviewed tracking recovery

The phone distinguishes the PC service's exact missing-job response (`404` with `OTB import job not found.`) from a proxy, unavailable server or arbitrary error page. The shared watcher caches that missing result and stops polling it, including across view remount. Retry loading explicitly starts a fresh owned read; older reads cannot replace the new observation. Ordinary read failures retain automatic retry and an immediate Retry loading action. A missing record describes the PC's response, not proof that no collector process remains.

Set aside search is available for confirmed missing jobs and readable-but-invalid/different-PC tracking records. Its inline review explains that any PC search is left running and imported games stay available. Back/Escape cancel the review, focus returns to its trigger, and completing recovery focuses the editable player field. Confirmation rechecks missing jobs; a recovered job is reopened, and an uncertain recheck preserves selection. Under the existing short Web Lock, it compares the exact reviewed canonical/legacy strings before one canonical write both stores their copy and records an idle selection. Failed writes preserve the original bytes. The idle record takes precedence over the old legacy mirror; malformed idle records without their saved details are refused. No PC start, Stop or delete request is sent by recovery.

Kept search details exposes an explicit JSON download containing the exact original strings. Undo set aside is available before choosing another search; it restores the previous tracking only if the selection and legacy mirror still match. Failed Undo retains the copy and can retry. A later new search carries previous details forward, while Undo refuses to overwrite it. These are local tracking copies, not copies of large PC game artifacts. Older frontend code refuses the new idle record rather than overwriting it; the PC service protocol is unchanged.

The shared operation survives leaving the view. Cross-tab changes during a review or its network recheck are retained. The phone also captures the canonical selection before FIDE preflight, so a delayed lookup cannot start an old request after another tab changes/replaces an idle selection. Reviewing recovery cancels local FIDE preflight; the PC is never started automatically by setting aside or restoring tracking.
