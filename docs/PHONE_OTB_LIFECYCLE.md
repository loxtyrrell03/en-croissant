# Phone OTB result lifetime

The PC job ID remains selected after Stop. If completion won the race, its saved artifact still loads and the games remain usable. If the PC confirmed a stopped/failed job, that result is visible and another search can be started. Cancellation does not request deletion of an artifact. The PC service intentionally terminates an active collector and reports a failed/stopped job; it does not promise desktop-style partial source results. This server contract is unchanged.

A Stop response invalidates an older shared status GET before starting a fresh observation. An abandoned request cannot replace the new result, clear its in-flight ownership or publish a late error. Status replies validate identity, supported state and supplied request metadata; completed jobs require usable player/year metadata. Compact completed status is distinct from an artifact already loaded: pending or failed artifact reads do not claim there are zero usable games. Shared watchers continue retrying read failures. Errors from Stop or Analyze survive ordinary status refreshes.

The phone waits for a stored job to load before allowing another search and restores that job's player, FIDE ID and year. Stop and Analyze have synchronous request guards and reject late component updates after unmount. A pending Stop never clears another view's persisted job selection. Completed games and source totals retain their scope. The panel reports PC-ready games; it no longer guesses browser/Prep handoff success from a storage receipt or says Saving indefinitely. Automatic Prep handoff recovery remains a separate follow-up.

The existing Mantine interface now wraps source/search button labels and shows complete game names and event metadata on narrow screens. The PC explanation is shorter and retains the need to leave the PC on. Source selectors, year controls, Stop, Analyze and saved result access remain available. This is a small correction within the existing phone design, not a new visual system.

## Recoverable PC start endpoint

`PUT /api/otb-import/jobs/otb-<UUID-v4>` accepts the same normalized search payload as the existing POST endpoint. The client must generate and durably retain the job ID and original request before sending it. A retry must use that exact ID and payload. There is no automatic fallback to POST: older PC services return 405 for this new route, which must become a visible compatibility error in the future phone integration. The phone integration below now persists and sends those recoverable requests.

The service owns each ID before asynchronous availability/storage checks, so concurrent retries join one start. Changing the player, FIDE ID, start year or selected sources for an existing/pending ID returns 409. Invalid client IDs return 400; the generated legacy POST IDs remain supported for reads and cancellation. Existing running, completed and stopped jobs are returned without another collector, even if the native binary is no longer installed. Repeated requests preserve result artifacts and completion timestamps. Explicit new searches use new IDs.

An initial save failure launches nothing and can retry the same queued destination. A synchronous pre-process launch failure can also retry. If the process was launched but its status save failed, a retry persists that existing job instead of spawning again. Stop that completes during an initial save prevents a later launch. These guarantees cover retries within the owning service and saved jobs loaded by its existing restart recovery. They do not claim an atomic process-spawn/filesystem transaction: a crash before the PID becomes durable retains the existing recovery limitation. Restarted interrupted jobs remain failed and require an intentional new search; retrying their old IDs never restarts them.

Scoped lint has zero warnings/errors. The service uses explicit child-process fixtures and owned temporary files; the actual HTTP test launches and closes a separate loopback home server with all data paths isolated and no collector installed. It discards one accepted reply, retries concurrently, rejects conflicts/invalid IDs, checks unavailable and legacy routes, and retains the completed artifact. It makes no upstream requests. ## Phone request ownership and retry

The phone now uses the recoverable PUT endpoint. `otbStartSession.ts` owns the complete versioned `encroissant-web-otb-start` record: random UUID, original player/FIDE/year/sources, PC endpoint and acknowledgement state. A durable write must succeed before any start is sent. One session promise remains alive when the import view closes; returning to the view observes that same operation. After a full reload, an unacknowledged record restores its fields and offers Retry connection. Retry never reruns FIDE resolution or substitutes edited input, a new ID or POST. Older PC services return an actionable update error. A different request/ID in the start reply is rejected.

A failed confirmation write keeps the already-saved request. The known PC job remains usable within the session, and retry saves its acknowledgement without another network start; after reload, PUT recovers that same ID. The acknowledged record is authoritative. Failure to update the legacy ID mirror cannot undo it, and WebApp now subscribes to the shared selection rather than polling that mirror. Receipt reads in its existing Prep callback are caught so they cannot escape through this subscription; the complete automatic Prep/state-persistence workflow is not certified by this change and remains below.

Same-origin storage changes update other open views. [Web Locks](https://www.w3.org/TR/web-locks/) coordinate the short synchronous selection writes; no network request holds a lock. A changed ID/request prevents a late reply from replacing newer selection. A pending record prevents another tab from silently replacing the uncertain search. New starts/reconnections require secure browser support for Web Locks and UUID generation; unsupported contexts expose guidance before mutation. Previously saved job reads remain available. Corrupt records and records belonging to another PC endpoint are preserved and refused, not overwritten. There is no repair/reset UI for those records in this milestone.

Start/status/Stop responses and JSON bodies have a 15-second deadline with cancellation propagation. Artifact bodies have a separate ten-minute bound so the small-status deadline does not interrupt large saved results. A timeout keeps the PC identity and permits another read; it does not stop or delete the independent PC collector. Downloads are retried from the beginning; range resumption and stalled-transfer progress remain broader performance/UX follow-ups.

The phone shows one Connecting/Retry action while a start is uncertain and explains that retry reconnects to the same search. Fields and source controls remain locked to that request. Locked input text now uses the existing theme's readable text colour, and the narrow input font follows the user's Mantine scale rather than staying fixed at 16px. The form's existing layout, sources, Stop and game actions are retained.
